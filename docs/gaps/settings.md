# `/settings` vs `account-settings`

**Template:** `design-system/templates/account-settings/AccountSettings.dc.html` — self-service profile page: a role pill next to the "Account Settings" title, then one card with First Name / Last Name / Email (with a Verified / Unverified pill inside the email input) / a read-only-by-policy Role select, "Account created" / "Last updated" metadata, and Save Changes / Reset buttons.
**App:** `/settings` → `src/app/settings/page.tsx` (wrapped in `src/components/ProtectedRoute.tsx`); API `src/app/api/users/[id]/route.ts` (GET, PATCH); schema `src/db/schema/users.schema.ts`. The stub `/profile` → `src/app/profile/page.tsx` renders a Name + Email form whose submit only `console.log`s; **the template subsumes it** — everything `/profile` shows (name, email) is a strict subset of the settings template, nothing in `src/` links to `/profile` (grep for `/profile` outside its own folder returns nothing), and `docs/AUDIT.md` 5.4 already recommends deleting it. Treat `/profile` as superseded by this template rather than as a second conversion target.
**Data sources the app uses today:** table `users` (`id`, `first_name`, `last_name`, `email`, `hashed_password`, `reset_token`, `reset_token_expiry`, `role`, `region`, `job_title`, `is_active`, `created_at`, `updated_at`) via client-side `fetch` of `GET /api/users/[session.user.id]`, which returns `{ user: { id, name, email, role, region, jobTitle, isActive, createdAt, updatedAt, firstName, lastName } }` (`firstName`/`lastName` are re-split from a `CONCAT(first_name, ' ', last_name)` alias); `PATCH /api/users/[id]` with `{ firstName, lastName, email, role }` returns `{ success, message, user }` (all columns minus `hashedPassword`, `resetToken`, `resetTokenExpiry`); `useSession()` from next-auth for the id and for `update()` after save.

## C. Notes

- **Ambiguities in the template.** (1) The `@template` description says role is "(read-only)" and the helper text says to contact an administrator, yet the `Select` is enabled and bound to `setRole`. Read it as "editable control, disabled by policy"; the data-script `$preview` props expose `role` as an enum editor for previewing each state, not as a user-editable field. (2) The role enum is `admin | staff | partner`; the app's `UserRole` type and API validation use `admin | user | partner`. `staff` is a label, not a value — do not introduce it into `users.role`. (3) `emailVerified` is a preview prop defaulting to `true`; there is no logic behind it. (4) `firstName` / `lastName` / `email` in the mock are hard-coded (`Joseph`, `Masongsong`, `jmasongsong@bchousing.org`) and `saveChanges` is a no-op. (5) `createdDate` / `updatedDate` are preview strings (`5/23/2025`, `7/15/2025`). (6) The data script computes a `year` value that nothing in the markup uses — a leftover, probably from a footer that was removed.
- **Mock-only elements.** Header "JM" / "Joseph Masongsong", the three seed values above, and the fixed dates.
- **App data / behaviour the template dropped:**
  - Success and error `Alert`s (`Profile updated successfully!`, `Failed to load user data: {status}`, `Network error occurred`, and API messages such as "Email is already taken", "Invalid email format", "Only admins can change roles").
  - Both loading states (`ProtectedRoute`'s `Loader2` card and the in-page CSS spinner) — the template is static.
  - "Saving..." pending label and the `disabled={isSaving}` state on every control.
  - Per-role icons (`Shield` / `UserCheck` / `User`) in the badge and in the select options, and the per-role badge colour (`destructive` for admin, `secondary` for partner).
  - Admin self-service role change (the select is enabled when `currentUserRole === 'admin'`) and the conditional helper "Only administrators can change user roles."
  - Input placeholders ("Enter your first name" / "Enter your last name" / "Enter your email").
  - Session refresh after save (`update({ ...session, user: { name, email } })`) so the header name updates without re-login — invisible UI, must be kept.
  - Ten leftover `console.log` calls in `settings/page.tsx` (noted in `docs/AUDIT.md`) — not UI, but they go with this file.
- **App data the page does not show but already has.** `GET /api/users/[id]` returns `region`, `jobTitle` and `isActive`; neither the current page nor the template displays them (they are admin-managed via `/admin/users` → `EditUserDialog`). No gap, just worth knowing the payload is larger than the form.
- **A data-shape quirk worth flagging during conversion.** `GET /api/users/[id]` selects `CONCAT(first_name, ' ', last_name)` and then re-splits on the first space to produce `firstName` / `lastName`, so a two-word first name is returned with its second word moved into `lastName`; saving then writes that split back via `PATCH`. The template's two separate fields will make this more visible, not less. Selecting `users.firstName` / `users.lastName` directly would fix it (the columns exist), but that is an API change outside a visual pass.
- **`/profile` disposition.** `src/app/profile/page.tsx` has a single "Name" field (from `session.user.name`), an Email field, "Save Changes" + "Cancel", and no API call. Every element maps onto the settings template (Name → First/Last, Email → Email, Save → Save Changes, Cancel → Reset), and the settings page already persists all of it. The template should be applied to `/settings` only; `/profile` can be removed (per `docs/AUDIT.md` 5.4 / 5.6, step 11) or redirected to `/settings`. `ProtectedRoute` would then be used by exactly one page.

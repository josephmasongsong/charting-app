# /admin/users/[id] (no app route) vs `user-detail`

**Template:** `design-system/templates/user-detail/UserDetail.dc.html` — admin read view of one user: large avatar tile with full name, a column of `ProfileField`s (Role, Region, Job Title, E-mail, Account Status), a "Developments (N)" list of the sites the user is assigned as primary, header buttons "Reset password" and "Edit user", and the same Edit modal as the user-management template.
**App:** **There is no app route for a user detail page.** `src/app/admin/users/` contains only `page.tsx`, `AdminUsersPage.tsx` and `components/`; no `[id]` folder exists, and `docs/AUDIT.md` §5.2 lists `user-detail` as "template is a page, app has a dialog". Closest live equivalents compared below: admin edit → `src/app/admin/users/components/EditUserDialog.tsx` (opened from `UsersTable.tsx`); self-service view/edit → `/settings` at `src/app/settings/page.tsx`; schema → `src/db/schema/users.schema.ts` and `src/db/schema/sites.schema.ts`.
**Data sources the app uses today:** `EditUserDialog` receives the row object from `GET /api/admin/users` and writes with `PATCH /api/users/[id]`; `/settings` reads `GET /api/users/[id]` (own id only) and writes with the same `PATCH`. Neither reads the `sites` table.

## C. Notes

- **No route, no link.** Nothing in the app navigates to a per-user page; `UsersTable` names are plain text and `EditUserDialog` is the only per-user surface. The user-management template links each name to this page, so the two templates must be adopted together or the link dropped.
- **"Primary" assignment is implicit.** `sites.user_id` is a single required FK, so every site has exactly one assigned user and there is no primary/secondary distinction to model. The template's "assigned as primary" wording maps directly to `sites.user_id = users.id`. No join table exists.
- **Sites-by-user query exists only as a page filter.** `src/app/sites/page.tsx` already builds the exact `WHERE sites.user_id = ?` query and a distinct-organizer list for its `userId` dropdown; an API version would be a lift of that code, not new logic.
- **Template role prop is `"User" | "Administrator"`** — the detail view has no Partner state, while the edit modal inside it offers `partner`. The DB has three roles.
- **Mock-only content.** "Flora Wong" / "FW", `fwong@bchousing.org`, region "LMDM", job title "People, Plants & Homes", the three `DEVELOPMENTS` (Sunrise Court, Harbourview Manor, Maple Ridge Commons with addresses, unit counts and statuses), and the header "Joseph Masongsong / JM" are hard-coded. `saveEdit` only closes the modal; nothing is persisted in the template.
- **Job-title spelling** in this template ("People, Plants & Homes") differs from both the DB value (`People Plants & Homes`) and the user-management template ("People, Plants and Homes").
- **App data the template dropped (important):**
  - **Region in the edit modal** — `EditUserDialog` has an admin-only Region `Select`; the template's modal omits it (the read view does show Region).
  - **`createdAt` / `updatedAt`** — `/settings` shows "Account created" and "Last updated"; `UsersTable` shows Created. The template shows neither.
  - **"Tenant Support Worker"** job title option — valid `UserJobTitle`, absent from the template's select.
  - **Role-gated helper text** ("Only admins can change roles" / "Only administrators can change user roles.") and the disabled-role behaviour for non-admins — the template assumes an admin viewer with everything editable.
  - **Success / error `Alert` banners**, the "Updating..." pending label, and the loading spinner — none designed.
  - **`/settings` "Reset" button** that restores the form to the fetched values — no equivalent.
  - **Password-related columns** (`hashed_password`, `reset_token`, `reset_token_expiry`) are correctly hidden by both `GET` routes; the template's "Reset password" button is the only place they surface, indirectly.

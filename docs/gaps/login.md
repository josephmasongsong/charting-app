# /login vs `sign-in`

**Template:** `design-system/templates/sign-in/SignIn.dc.html` — full-bleed action-blue page, one centred 480px white card: logo + "BC HOUSING" wordmark, optional danger alert, email/password form, "Sign in" button, "Forgot your password?" link. No header, no footer, no loading state.
**App:** `/login` → `src/app/login/page.tsx` (current working-tree version, after the visual pass). Chrome from `src/app/layout.tsx` (`Navigation` returns `null` without a session; the inline `<footer>` always renders) and `src/components/ClientAuthGuard.tsx` (renders its own loading card before the page mounts).
**Data sources:** `signIn('credentials', { email, password, redirect: false })` → `CredentialsProvider` in `src/lib/auth.ts` (`users.email`, `users.hashed_password`, `users.is_active`); `useSession()` for the already-signed-in redirect; `middleware.ts` and NextAuth `pages.error` can both land here with `?error=…`.

Already matching after the visual pass (not repeated below): blue field with `48px 24px` padding; 480px card with `--radius-card`, `40/48/44px` padding, no border or shadow; `BrandMark` (34px DS logo) + 24px/700 teal wordmark; 14.5px/600 labels with 6px gap; 32px form offset and 24px field gap; inputs at 40px, `--radius-input`, `--border-input`, 15px, placeholders "Enter your email" / "Enter your password", `autoComplete` hints; submit at 15.5px/400, `11px 18px`, `--action-primary` → `--action-primary-hover`, `--radius-control`; action-blue 14.5px "Forgot your password?" outside the form; alert placed between brand block and form with the DS red-bar treatment.

## A. Visual differences — same data, different presentation

| Region of page | Template | App today | Notes |
|---|---|---|---|
| Page height / footer | The blue field is the whole viewport (`min-height:100vh`); nothing below it. | Root layout wraps the page in `<main className="min-h-screen bg-background">` and appends the app-wide `<footer>` ("© Copyright 2025." + support `mailto:`), so the blue field is 100vh tall and a grey footer bar sits under it. | Layout-level, affects every auth page. Fixing it means suppressing or restyling the footer on `/login`, `/forgot-password`, `/reset-password/*`, `/` — a `layout.tsx` decision, not a page change. |
| Pre-mount loading card | None. | `ClientAuthGuard` shows its own `flex min-h-screen … Card w-full max-w-md` "Loading..." card (old shadcn look, white page) before `/login` renders; the page's own "Loading..." / "Redirecting to dashboard..." cards are now on the blue field. | So the first paint is still the old style. `ClientAuthGuard` is shared by every route. |
| Input text size at ≥768px | 15px at every width. | `ui/input` keeps its base `text-base md:text-sm`; the page adds `text-[15px]`, which only overrides the base size. At the `md` breakpoint `md:text-sm` still applies, so on desktop the inputs render at `--text-sm` = 13px. | Needs `md:text-[15px]` on the page's `inputClass` (or a DS-sized input variant). Mobile is correct. |
| Input focus / placeholder | DS `Input` has no focus ring (only `outline-offset:-1`) and browser-default placeholder colour. | shadcn `focus-visible:border-ring focus-visible:ring-[3px] focus-visible:ring-ring/50` (grey `--ring`) and `placeholder:text-muted-foreground`. | Cosmetic; the DS `Select` uses `0 0 0 3px var(--action-selected)` + `--action-primary` border on focus, which would be the consistent choice. |
| Input disabled state | Not designed (template inputs are never disabled). | shadcn `disabled:opacity-50 disabled:cursor-not-allowed` while `isLoading`. | Behaviour is required (kept); only the disabled *look* is undesigned. |
| Submit button shadow | Flat fill, `border:1px solid transparent`. | shadcn `default` variant keeps `shadow-xs` under the token overrides. | Add `shadow-none`. |
| Submit button disabled state | Not designed. DS `Button` disabled = flat `--action-primary-disabled` fill, white text, no opacity change. | shadcn `disabled:opacity-50` while `isLoading` ("Signing in..."). | Behaviour kept; look differs from the DS disabled rule. |
| Error alert border | `--danger-surface` box with a 5px `--danger` left border only; no other border; 14px text; radius unspecified. | `Alert variant="destructive"`: same fill and left bar, but the base `border` (1px `--border` grey on the other three sides) remains, corners are `rounded-[2px]`, and text is `text-sm` = 13px. | Cosmetic: `border-y-0 border-r-0` and `text-[14px]` would close it. Same `error` string on both sides. |
| Logo `alt` | `alt="BC Housing"`. | `BrandMark` renders `alt=""` (decorative) and the wordmark carries the name as text. | Accessibility choice, not a visual one; either is acceptable. |
| Landing page `/` | Not in the template; the sign-in card is the first screen. | `src/app/page.tsx` still shows the old "Welcome" `Card` with "Sign In" / "Forgot Password?" buttons before `/login`. | Separate route (`docs/AUDIT.md` §5.4 says extrapolate from `sign-in`). |

## B. New UI with no data behind it

| Element (template label/binding) | What it shows | App has? | Needs | Detail |
|---|---|---|---|---|
| `{{ alertMessage }}` / `{{ hasAlert }}` | A page-level message above the form, driven by whatever the page was opened with. | Partly — the alert markup is rendered (with a `// TODO: not wired` comment) but only for the page's own submit errors. | **client state** | Two real messages never reach the slot: (1) `middleware.ts` redirects deactivated users to `/login?error=account_deactivated` and the page never reads `useSearchParams()`; (2) `auth.ts` `authorize()` throws "This account has been deactivated. Please contact your administrator.", which comes back in `result.error`, but `handleSubmit` replaces every error with "Invalid email or password". NextAuth's `pages.error = '/login'` (`src/lib/auth.ts`) sends provider errors here with `?error=` too. No new data — read the query string and stop flattening `result.error`. Out of scope for a visual pass because it changes behaviour. |
| Alert copy for the deactivated case | Wording for the URL-driven message. | No — the template's slot is an empty editor prop. | **cosmetic** | Pick the sentence when the slot is wired; today the only strings are "Invalid email or password" and "An error occurred. Please try again." |

Everything else in the template (wordmark, blue field, `autoComplete` hints) was cosmetic and is now rendered; the mock's `onSubmit` (unconditional navigation to the dashboard template) has no app equivalent and needs nothing.
